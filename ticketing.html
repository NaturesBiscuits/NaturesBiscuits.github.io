A full-stack event ticketing platform. Fans pick seats on a real-time seat map, hold them for 10 minutes, check out with simulated test cards and get a QR door pass. Organizers manage venues, section pricing and gate check-in.

Built for high-concurrency inventory management: in a flash-sale spike, hundreds of buyers contend for the same database rows at the same instant. Every booking write is an ACID transaction in a SECURITY DEFINER PL/pgSQL function, using pessimistic row-level locking (SELECT … FOR UPDATE), deterministic lock ordering to prevent deadlocks, and constraints as the last line of defence. Overselling a seat, half-holding a group and duplicate orders are ruled out by the database itself, not by application code.

Try it as a guest: click the screenshot, press Sign in, then Fill in the sample account. Payments are simulated, so nothing is ever charged.

01 · Real-time state synchronization

Every fan sees the same map, live

  • WebSockets
  • Pub/sub broadcast
  • Presence tracking
  • Event-driven DB triggers
  • Cache revalidation

Recorded with two separate browser sessions on the live site. Fan 1 selects and reserves seats; Fan 2’s map shows the selection, then the hold, without a reload.

Selected by another fan (presence)HELD for 10 minutes

How it works

  • Database push. A statement-level AFTER UPDATE trigger on event_seats diffs the transition tables and calls realtime.send() once per statement on event:<id>:seats. The payload is only {seatId, status}: no owners, prices or reservation ids.
  • Hints, not truth. A broadcast patches the TanStack Query cache with setQueryData, then invalidates it so the authoritative snapshot is refetched, as it always is after a reconnect. A failed broadcast is caught and can never roll back a booking.
  • Presence. Each tab joins event:<id>:viewers under a random key and tracks its selected seat ids, throttled to one update every 2 s. No user ids leave the browser.
  • Expiry on read. A HELD seat past held_until reads as available in every query, so correctness never waits on a job; pg_cron only tidies rows once a minute.

How one race runs

What every request runs (simplified reserve_seats)

-- one transaction per request
SELECT 1 FROM event_seats
 WHERE seat_id = ANY(seats)
 ORDER BY seat_id
   FOR UPDATE;                -- wait for the row lock

UPDATE event_seats
   SET status = 'HELD',
       held_until = now() + interval '10 minutes'
 WHERE seat_id = ANY(seats)
   AND status = 'AVAILABLE';    -- only seats still free

IF row_count <> cardinality(seats) THEN
  RAISE 'SEAT_UNAVAILABLE';     -- undo it all: all or nothing
END IF;

Locking in seat_id order means two overlapping group requests always queue in the same order, so they can’t deadlock.

03 · Seat-allocation algorithm · Simulation

The group seating algorithm

  • Heuristic search
  • Weighted cost function
  • Greedy expansion
  • Atomic multi-row holds
  • Contention-aware ranking

This is the lab’s group seating simulation, not a real sale: 6 to 24 bot fans, each booking for a party of 1 to 4, request overlapping seats at the same instant. It runs the same code a real booking does: reserve_seats in Postgres and the seat planner from the booking dialog.

How it works

  • Atomic hold. The same reserve_seats as above. A group’s rows are locked and claimed in one transaction; if row_count is short, the whole group is rolled back. A group is held whole or not at all.
  • Candidate search. The planner (findGroupPlans(), TypeScript in the browser) maps seats to coordinates and generates three tiers: contiguous runs in one row, runs stacked over 2 to 4 consecutive rows (every split of the party size), and greedy nearest-seat growth from up to 60 seeds.
  • Ranked by cost. Every candidate gets a cost; the lowest is offered as the best match, as shown below.

How a group race runs

How options are ranked

cost  = shape + 4·dist + 30·Δprice + 12·eyed
shape = 0 one row · 40+ stacked · 120+ scattered
dist  = |Δx| + 1.5·|Δrow|  // to the seats you wanted
eyed  = seats other fans have selected right now

Simplified from findGroupPlans(). It runs in about 10 to 20 ms on a 660-seat venue and only advises; Postgres decides every hold.

How a seat is sold exactly oncePostgres functions, locks and constraints

Every multi-row operation is one Postgres function, so it either fully happens or not at all. The second fan never waits; they get SEAT_UNAVAILABLE the moment the first one commits.

  1. Hold

    reserve_seats locks seat rows in a fixed order, so overlapping requests can't deadlock, then claims only free ones with one conditional UPDATE. Fewer rows than asked for rolls everything back.

  2. Pay

    start_payment records a pending payment for the held amount. No lock is held while the fan pays, and an idempotency key makes retries return the same payment.

  3. Confirm

    complete_payment runs server-side: seats go held to sold, an order and one ticket per seat are created. A replayed webhook returns the same order.

  • Constraints as the last line of defence. One ticket per seat per event and one order per reservation are unique constraints; a CHECK makes impossible seat states unrepresentable.
  • No ghost seats. An expired hold reads as available everywhere at once, even before the pg_cron cleanup runs. A payment that lands after its hold lapsed is refunded and sells nothing.
  • Door check-in is a single UPDATE ... WHERE status = 'VALID': two gates scan one pass at once, one admits, the other is refused.
  • Deliberately single-region. A second writer region would let both sides of a network partition sell the same seat, so inventory keeps one writer per event.

  • A read-only Postgres terminal shows each request's backend process id, transaction id and the database's own clock: 100 requests served by about 10 pooled connections as 100 separate transactions. Nothing in it is typed or simulated by the page.
  • The database audits itself. After every run it checks for seats in two holds, partial holds, extra orders, duplicate tickets and double admissions, and the result goes on a public scoreboard.
  • Safe on a free tier. Runs are budgeted in the database (3 per visitor every 10 minutes, 60 per hour site-wide), visitors are an HMAC of their IP address, and bots can only act on a hidden sandbox event.

For organizers

  • Venues and seating. Sections, rows and seats with a layout preview.
  • Events and pricing. Per-section price tiers and per-seat inventory. Published events are frozen by database triggers, so nothing changes under a fan mid-checkout.
  • Door check-in. Paste or camera-scan a pass; the first scan admits and later scans say where and when it was used.
  • Analytics. Sales and reservation statistics aggregated in the database.

  • Database rows never reach React. Mappers convert UUIDs, price tiers and flexible seat labels into domain types.
  • Money is integer PHP centavos end to end, from the database BIGINT to the forms.
  • Double-submit guard. A synchronous hook blocks repeated reserve and confirm clicks before a request leaves the browser; the database remains the real guarantee.
What the database enforcesKeys, constraints and row-level security
  • One row per seat per event. event_seats has the composite key (event_id, seat_id) and a status of AVAILABLE, HELD or SOLD, with held_until and reservation_id recording who holds it and until when. This is the table the booking functions lock.
  • One order per reservation and per payment. orders.reservation_id and orders.payment_id are both unique, so a replayed webhook cannot create a second order.
  • Venues can't be mixed up. Composite foreign keys carry venue_id through seats, price tiers, events and event seats, so a seat from one venue can't be sold for another venue's event.
  • Money is integer minor units. price_minor, amount_minor and total_minor are bigint and capped at 253−1, the largest integer JavaScript can hold exactly.
  • History survives edits. Reservation items and tickets store their own copy of the section, row, seat and price.
  • Every door scan is logged. ticket_scans records the gate and a result of ADMITTED, ALREADY_USED, INVALID, WRONG_EVENT or CANCELLED. A ticket's check_in_secret defaults to a random value.
  • Roles are constrained. profiles.role is CUSTOMER, ORGANIZER or ADMIN, and organizer membership is OWNER, EDITOR or VIEWER.
  • Sandbox rows are flagged. is_sandbox on venues and events keeps the Concurrency Lab's data out of the public catalogue.
  • Row-level security on all 17 public tables. The 4 private tables hold lab runs, the lab lease, the demo account and run-budget visits. The anon and authenticated roles have no privileges on them, so only server-side code reaches them.
  • Logic lives next to the data. 63 functions across the two schemas (29 public, all SECURITY DEFINER; 34 private), 20 triggers, and 2 pg_cron jobs: held seats are released every minute and the demo account is reset daily.
SecurityRow-level security, secrets and passes
  • Row-level security on every table. Client writes go through SECURITY DEFINER functions in a private schema that check who is calling.
  • Roles can't be self-assigned. Sign-up always creates a Customer; organizers are promoted in trusted SQL.
  • Secret keys stay on the server, and the build is checked to confirm they never reach the browser bundle.
  • Door passes can't be forged. The pass secret is never a readable column, and a wrong secret and an unknown ticket give the same answer.
  • Realtime leaks nothing. Seat broadcasts carry only a seat id and a status.
  • Payments are always simulated. No card number is stored, only the last four digits.

What I learnedLessons from building it
  • Test through the real API, not only in SQL. The first lab run failed with UPDATE requires a WHERE clause: Supabase's API connections load pg_safeupdate, which my pgTAP suite (running as postgres) doesn't. Exercising the route against the real stack caught it.
  • Make deadlocks impossible rather than rare. Locking seats in a fixed order means overlapping group requests can't wait on each other.
  • Know what you're not building. Multi-region writes were out of scope on purpose; I documented the split-brain tradeoff instead of faking it.
  • A public demo needs guardrails. Run budgets, hashed visitor ids and a sandbox event keep a free-tier database safe from the very visitors it invites.
